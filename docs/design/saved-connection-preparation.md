# 保存済み接続の準備 Small Development

## 現在のユースケース

- Given: 保存済み接続が選択されている。
- When: 利用者が接続を確定する。
- Then: 保存した秘密情報を復元した接続を実行し、既存の接続結果を表示する。
- Failure: 復元に失敗したら接続せずエラーを表示する。準備中に中止されたら実行しない。

## 最小の協調

画面が接続準備へ依頼し、返された準備済み接続を実行する。
準備と実行を分けるのは、秘密情報の取得を待つ間にも中止できるようにするため。

## 今必要な契約

接続準備:
- accepts: 準備の依頼
- provides: 準備済み接続

準備済み接続:
- accepts: 実行の依頼
- provides: 既存の接続結果

画面は準備済み接続からパスワード、認証方式、接続パラメータを取得しない。
既存の成功・失敗・中止の結果契約は変更しない。

## 今はモデル化しない差異

- DB製品別の認証能力一覧、継承階層、動的レジストリ
- MongoDB/DuckDBの未実装の接続仕様
- パスワードや識別子を取り出す新しいドメインgetter

## Creation Boundary

`createSavedConnection` が既存の保存形式・秘密情報取得Provider・接続Storeを契約へ組み立てる。
Factoryの生成時には取得も接続も実行しない。
秘密情報は準備時に取得し、接続設定は準備済み接続の内部へ閉じる。
関連する実装群を選ぶ必要はないためAbstract Factoryは作らない。

既存Provider/Storeとの境界では、既存のDTOとIPC契約をそのまま使用する。
新しい2契約にDTO、DB種別、認証フラグや秘密情報のgetterは公開しない。
既存プロジェクト全体の保存形式をこの修正で作り直さない。

## Contract-only Walkthrough

- 正常系: 画面が準備を依頼 → 準備済み接続を受け取る → 中止されていなければ実行 → 結果表示。
- 復元失敗: 準備が失敗 → 画面でエラー表示。実行可能な接続は返らない。
- 中止: 待っていた準備が完了しても、画面はその接続を実行しない。
- 接続失敗: 実行結果をそのまま表示。別の認証へのフォールバックや自動再試行はしない。

いずれも画面にDB種別・認証方式・パスワードの有無の判断は不要。

## #718の原因と前案からの変更

ObjectTreeがWindows認証フラグだけでパスワード復元を省略していた。
前案はDB種別の条件をツリーとreducerに追加したが、画面側が認証方式を解釈する責務を残した。

今回、その条件を撤去した。保存パスワードの復元は編集画面と同じ保存設定に従う。
保存設定が無効なら復元しない。取得した空パスワードの許否も画面やFactoryでは判定しない。
保存設定が有効なら、Windows認証フラグにかかわらず復元する。

既存の接続文字列生成はPostgreSQL/MySQLでパスワードを使用し、
SQL ServerではWindows認証指定時にTrusted_Connectionを使用する。
その既存の解釈をFrontendに複製しない。SSH情報の復元は従来の処理をFactory内へ移す。

DB種別変更時は以前のWindows認証選択をリセットする。
切り替え先DBごとの判定はなく、SQL Serverを選び直した場合も利用者が明示的に選択する。
保存済みプロファイルに残っているフラグは書き換えず、パスワード復元を妨げないようにする。

## 次の要求まで決めないこと

新しいDBのドライバ、接続先入力、保存形式は、その対応時に設計する。
今回の準備・実行契約を満たせるなら画面の接続フローは変更しない。
新たな接続方式が今の契約では表現できない場合に限り、必要な操作を追加する。
全ての将来DBが既存のIPCや保存形式のままで対応できるとは保証しない。

## 検証

- 実際のツリー・編集画面・Storeを使い、残存フラグがあっても同じ保存パスワードを送信すること。
- 未保存パスワードを取得しないこと、SSHの各取得経路、取得失敗時に接続しないこと。
- 準備完了だけでは接続せず、実行操作だけが既存Storeを呼ぶこと。
- 中止中に秘密情報取得が完了しても接続しないこと。
- DB切り替えで以前の認証選択を引き継がず、Windows認証を再選択できること。
