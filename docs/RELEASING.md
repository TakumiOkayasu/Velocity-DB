# リリースとバージョンの運用

Issue: #737

この文書はリリース可否と版数の判断基準である。マージ自体はタグ作成、公開、workflowの変更を許可しない。公開するSHAと版数は、リリースごとに人間が承認する。

## リリースするタイミング

通常は、利用者に届ける変更のまとまりが完成し、下記の出荷条件がすべて満たされた時点で候補を作る。PRのマージ件数、経過日数、依存更新の件数だけでは公開しない。変更を待ち続けないよう、月1回は未リリース差分を確認し、候補の作成または見送り理由をissueに残す。これは自動公開の周期ではない。

データ損失、認証情報漏えい、接続・起動不能など、既存リリースの重大な問題を直した場合は通常のまとまりを待たずに修正版を候補とする。ただしテスト、復旧確認、公開承認は省略しない。内部整理や開発依存の更新だけで配布物の利用者に影響がなければ、それだけを理由に公開する必要はない。

## 版数と利用者への互換性

[Semantic Versioning 2.0.0](https://semver.org/)のMAJOR.MINOR.PATCHを採用する。デスクトップアプリである本製品では、公開契約を次の利用者向け保証として定義する。

- 文書化したOS・DB・ドライバ・実行環境の対応範囲。
- 保存済み接続プロファイル、設定、セッションと、入出力ファイル形式の利用継続。
- 文書化したSQL実行・編集・保存・エクスポート操作の意味と、データ保護上の保証。
- 外部公開すると明示したインターフェース。内部IPCや非公開クラスの形は、それだけでは公開契約ではない。

| 変更 | 版数 | 例 |
| --- | --- | --- |
| 公開契約を維持した不具合・脆弱性の修正 | PATCH | 接続不能、設定未反映、誤表示の修正 |
| 公開契約を維持した新機能、公開機能の非推奨化 | MINOR | 新しいDBや編集機能の追加。PATCHを0に戻す |
| 公開契約の破壊的変更 | MAJOR | 旧設定の利用不能、利用者に必須の手動移行、対応環境の廃止、既存操作の互換性を壊す変更。MINOR/PATCHを0に戻す |

複数の変更を含む場合は、前回の正式リリースからの差分のうち最も大きい区分を採用する。自動移行だけで既存利用が継続する追加機能は、移行の存在だけを理由にMAJORにはしない。ただしバックアップ・復旧可能性と旧版へ戻せる範囲は出荷条件として確認する。

「安定してきた」「変更が多い」「内部を全面改修した」だけで2.0.0にはしない。すでに公開した版数の意味を後から変更したり、過去のタグを付け直したりしない。

次回版数はこの方針の導入と同時に決めない。直前の正式リリースと候補SHAを比較し、契約への影響をリリースPRに列挙して決める。最後が1.4.2なら、修正だけは1.4.3、互換追加なら1.5.0、破壊的変更があれば2.0.0という判断になる。

## バージョンの正本とタグ

製品の数値バージョンの正本は、ルート`CMakeLists.txt`の`project(VelocityDB VERSION ...)`とする。正式タグは、その値へ`v`を付けた`vMAJOR.MINOR.PATCH`だけを使用し、先頭ゼロや独自の別名を許可しない。表示・リソース・配布物に含まれる版数が正本と一致することを出荷時に確認する。

`frontend/package.json`はprivateな内部パッケージである。そのversionを製品タグに合わせて機械的に変更したり、第二の製品版数の正本にしたりしない。将来別配布する場合は、その公開契約を別途定義する。

タグは承認されたmain上の特定のcommit SHAに対して一度だけ作成する。移動するmainという名前だけを承認対象にせず、annotated tagの注記とリリース記録に対象SHAを残す。公開済みのタグは移動・再利用せず、実行ファイルやZIPも同じ版数で差し替えない。問題がある配布物は利用停止を案内し、新しい版数で修正する。

## 出荷条件

リリースPRまたはissueに、次の結果と証拠へのリンクを残す。

| Gate | 必須の確認 |
| --- | --- |
| スコープ | 前回正式タグから候補SHAまでの利用者向け変更、非目標、既知の制限、版数の理由がある |
| 検証 | 候補SHAに対応する必須CIが成功している。古いPR headの成功やrelease buildだけで代用しない。skipと未実施を明記する |
| Windows配布物 | 対応するWindows/実行環境で、配布相当のRelease構成の起動、版数表示、フロントエンド読込みを確認する |
| DB・データ保護 | 変更に関係する対応DBで接続、一覧、クエリ、変更・保存の正常系と失敗系を確認する。破壊的試験には専用の使い捨てDBを使い、実データでは行わない |
| 永続化 | 旧版のテスト用設定・プロファイル・セッションの読込みと、変更した永続化処理を確認する。実認証情報をfixtureや証跡へ入れない |
| 復旧 | 配布物を戻す手順、データ/設定を戻す必要性と制限が明記されている。旧版へ戻すだけで安全とは仮定しない |
| ブロッカー | 当該候補に関係する未解決の重大なデータ損失・漏えい・基本操作不能がない。無関係なopen issueがあるだけで無期限延期しない |
| 公開承認 | 公開担当者が候補SHA、版数、検証、既知の制限を確認し、タグpushと公開を明示承認した |

通常の検証コマンドと環境要件は`AGENTS.md`を参照し、この文書へ別系統のbuild/test手順を作らない。GitHubのRelease作成後は、実際に公開されたZIPについて内容・SHA-256・起動結果を確認し、候補との対応を記録する。

## 現行workflowとの境界

方針導入時の`.github/workflows/release.yml`は`v*`タグのpushを受けてbuildと公開へ進む。バックエンドは`BUILD_TESTS=OFF`であり、Release jobの成功はテスト成功の証拠ではない。タグ形式・CMake版数・必須CIの照合や人間承認が、このworkflowに自動実装済みだとは扱わない。

また、同workflowにはDraft/prereleaseの明示設定がない。`vX.Y.Z-rc.N`を試しにpushしてはならない。正式公開を避けて評価したい場合は、まず通常のCI artifactで候補を確認する。prereleaseを公開するには、タグ検証、正しいprerelease属性、artifactの対応、公開承認の経路を別のPRで実装・検証してから使用する。

この文書の追加だけでは、workflow・権限・タグ・バージョン・Releaseは変更されない。チェックの自動化を追加する際も、YAMLは配線に限定し、判定は既存のテスト可能なスクリプト群へ置く。
